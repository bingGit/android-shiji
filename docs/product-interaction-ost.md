# Android VoiceFlow 交互优化机会解决方案树

日期：2026-07-04

## 1. 背景

Android VoiceFlow 已经具备基础雏形：

- 实时录音与转写；
- 灵感卡片；
- 后处理模型调用；
- 底部主导航；
- 底部后处理操作栏。

当前主要问题不再是“有没有功能”，而是“能否作为一个可反复加工的创作者笔记空间使用”。测试反馈集中在交互粗糙、操作分散、内容不可编辑、状态反馈不清、历史不持久等方面。

本文件用 Opportunity Solution Tree 的方式，把用户反馈转化为下一阶段的产品设计与开发依据。

## 2. Desired Outcome

核心目标：

> 提升一次语音记录完成后的继续加工率，让用户愿意把原始语音灵感继续加工成可复制、可编辑、可保存的内容版本。

建议阶段性指标：

| 指标 | 说明 | 目标 |
|---|---|---|
| 记录后处理触发率 | 生成 final transcript 后，用户点击任一后处理动作的比例 | >= 60% |
| 单卡片版本数 | 每张灵感卡片平均生成的处理版本数量 | >= 1.5 |
| 结果复制率 | 后处理结果被复制的比例 | >= 40% |
| 结果编辑率 | 生成结果被用户手动编辑的比例 | >= 30% |
| 历史回访率 | 用户重新打开历史卡片的比例 | >= 25% |

现阶段没有埋点系统，可以先用手动测试和开发者观察替代，后续再接入本地事件日志。

## 3. Opportunity Map

### O1：我想快速找到常用操作，不想被一堆按钮打断

用户反馈：

- 记录完成后按钮太多；
- 不知道哪些是最重要的；
- 其他低频动作可以折叠或自定义。

机会判断：

这是高优先级机会。按钮过载会直接影响记录后的第一步动作，降低继续加工率。

### O2：我想在结果附近继续操作，不想上下滑动来回找按钮

用户反馈：

- 点击“提炼要点”后结果出现在下面；
- 想改动或换别的按钮时，需要滑到上面；
- 在卡片详情中也有同样问题。

机会判断：

这是高优先级机会。操作距离会影响连续加工效率，尤其是移动端单手使用。

### O3：我想把 AI 结果当草稿继续改，而不是只能复制

用户反馈：

- 生成内容后不能编辑；
- AI 输出通常只是初稿；
- 用户希望可以修改后再复制或保存。

机会判断：

这是高优先级机会。可编辑性决定产品是“生成器”还是“创作工具”。

### O4：我想打开一条记录后像进入一篇笔记，而不是刷消息流

用户反馈：

- 卡片 tab 中不同记录边界不明显；
- 打开一条记录后应该进入独立空间；
- 当前更像消息流，不像笔记；
- 缺少修改、删除等常规操作。

机会判断：

这是中高优先级机会。它影响用户是否愿意回看和继续加工历史灵感。

### O5：我想知道按钮点击后到底有没有在工作

用户反馈：

- 卡片中点击按钮没有交互状态；
- 不知道是失败、卡住还是正在处理；
- 这应是整个交互的核心基础能力。

机会判断：

这是基础体验机会，优先级高。所有异步动作都需要明确状态。

### O6：我不希望每次更新或重启后内容都消失

用户反馈：

- 当前似乎没有进行存储；
- 每次更新后之前内容没有了。

机会判断：

这是高优先级机会。没有持久化，产品无法进入真实日常使用。

## 4. Prioritized Opportunities

| 排名 | 机会 | 重要性 | 当前满意度 | 优先级原因 |
|---|---|---:|---:|---|
| 1 | O6 本地持久化 | 高 | 低 | 不保存就无法真实使用，影响信任 |
| 2 | O3 生成结果可编辑 | 高 | 低 | 决定产品是否能成为创作工具 |
| 3 | O5 统一状态反馈 | 高 | 中低 | 所有 AI/网络动作都依赖它 |
| 4 | O1 操作主次分层 | 中高 | 中 | 已部分改善，但还需要配置化和稳定交互 |
| 5 | O2 结果附近继续操作 | 中高 | 中低 | 影响连续处理效率 |
| 6 | O4 笔记化卡片详情 | 中高 | 中低 | 影响长期管理与回访 |

说明：

- O1/O2/O5 已经通过底部处理栏做了第一轮改善，但还需要继续完善。
- O6 和 O3 是下一阶段从“可演示”走向“可日用”的关键。

## 5. Solution Tree

### O1：快速找到常用操作

方案：

1. 底部主操作栏只展示 `复制 / 润色 / 提炼 / 更多`。
2. `更多` 用 Bottom Sheet 或展开面板收纳低频动作。
3. 支持用户自定义底部主操作，例如把 `生成标题` 替换成 `提炼要点`。
4. 根据内容智能推荐 2-3 个动作。

推荐下一步：

- 保留当前底部处理栏；
- 将“更多”从内联展开升级为 Bottom Sheet；
- 暂缓自定义，避免设置项过早复杂化。

实验：

| 假设 | 方法 | 指标 | 成功标准 |
|---|---|---|---|
| 常用动作收敛后用户更快触发后处理 | 让用户完成“记录后润色”任务，对比旧按钮网格 | 从记录完成到点击后处理的时间 | 缩短 30% |
| 低频动作折叠不会明显降低发现率 | 测试用户是否能找到“小红书风格” | 找到目标动作的成功率 | >= 80% |

### O2：减少上下滑动成本

方案：

1. 底部固定处理栏跟随记录页和卡片详情页。
2. 每个处理结果卡片自带 `复制 / 编辑 / 重新生成 / 删除`。
3. 生成结果后自动滚动到新结果。
4. 在结果区顶部提供“继续处理”快捷入口。

推荐下一步：

- 为处理结果卡片增加局部操作；
- 生成成功后聚焦最新结果；
- 保留底部处理栏作为全局动作入口。

实验：

| 假设 | 方法 | 指标 | 成功标准 |
|---|---|---|---|
| 结果局部操作能减少来回滑动 | 观察用户从生成结果到复制/再生成的路径 | 滑动次数 | 平均减少 50% |
| 自动聚焦最新结果更符合预期 | 生成后自动定位最新结果，让用户继续操作 | 用户是否能立即找到结果 | >= 90% |

### O3：生成结果可编辑

方案：

1. 处理结果从只读文本变成可编辑草稿。
2. 编辑后标记为“已修改”。
3. 支持保存编辑内容、复制编辑后内容。
4. 支持恢复 AI 原始版本。
5. 支持“用当前编辑结果继续生成”。

推荐下一步：

- 先实现处理结果可编辑；
- 保存编辑后的 content；
- 暂缓版本 diff 和恢复能力。

实验：

| 假设 | 方法 | 指标 | 成功标准 |
|---|---|---|---|
| 用户会编辑 AI 结果 | 记录 10 条真实使用，观察结果是否被修改 | 编辑率 | >= 30% |
| 编辑后复制更符合创作流 | 用户完成“润色后改一句并复制”任务 | 任务完成率 | >= 80% |

### O4：卡片详情笔记化

方案：

1. 卡片列表只展示摘要、时间、状态和操作入口。
2. 点击卡片进入详情空间，而不是在同页混合列表和详情。
3. 详情页明确分区：原文、处理版本、卡片操作。
4. 支持卡片重命名、删除、复制原文。
5. 后续支持标签、收藏、搜索。

推荐下一步：

- 先做详情页视觉重构，不一定引入真正路由；
- 列表和详情明确分离；
- 卡片边界更强，列表更像“笔记列表”。

实验：

| 假设 | 方法 | 指标 | 成功标准 |
|---|---|---|---|
| 笔记详情更容易理解 | 让用户找到某条历史并继续润色 | 成功率与完成时间 | 成功率 >= 90% |
| 明确卡片边界提升回访意愿 | 让用户浏览多条记录并选择一条继续处理 | 误选率 | <= 10% |

### O5：统一状态反馈

方案：

1. 每个后处理动作有独立状态：Idle、Running、Success、Failed。
2. 按钮显示“生成中...”。
3. 结果区显示占位/加载态。
4. 失败后在对应动作或结果区显示错误和重试。
5. 网络连接测试、录音、转写、后处理都复用统一状态表达。

推荐下一步：

- 当前已有 running action；
- 下一步改成 per-action 状态，避免全局状态过粗；
- 失败时保留最后一次错误并允许重试。

实验：

| 假设 | 方法 | 指标 | 成功标准 |
|---|---|---|---|
| 明确 loading 能降低重复点击 | 观察用户点击后是否重复点按钮 | 重复点击次数 | 下降 70% |
| 局部错误比全局错误更容易恢复 | 制造一次后处理失败，让用户重试 | 重试成功率 | >= 80% |

### O6：本地持久化

方案：

1. 使用 Room 保存 IdeaCard 和 ProcessingResult。
2. 或先用 JSON 文件轻量保存，后续迁移 Room。
3. 保存原始转写、处理结果、编辑内容、创建时间、模型信息。
4. App 启动时恢复历史。
5. 支持删除卡片和删除处理版本。

推荐下一步：

- 如果追求快，先做 JSON 文件存储；
- 如果希望后面稳定扩展搜索/标签，直接上 Room；
- 本项目后续会有多版本、编辑、搜索，更推荐 Room。

实验：

| 假设 | 方法 | 指标 | 成功标准 |
|---|---|---|---|
| 本地保存足够支撑 MVP | 使用一周，不接云同步 | 历史丢失次数 | 0 |
| 用户会回到历史卡片继续加工 | 保存历史后观察回访行为 | 历史卡片回访率 | >= 25% |

## 6. Recommended P0 Interaction Spec

下一阶段 P0 不追求更多 AI 模板，而是把核心“记录 -> 加工 -> 编辑 -> 保存”闭环做稳。

### 6.1 记录页

页面结构：

```text
顶部：状态 / 连接信息
主体：原始转写
底部：处理操作栏
底部导航：记录 / 卡片 / 设置
```

底部处理操作栏：

```text
[复制] [润色表达] [提炼要点] [更多]
```

更多：

```text
整理成文
提炼观点
生成标题
扩写段落
小红书风格
公众号开头
口播稿
```

交互要求：

- 点击后处理动作后，当前动作显示“生成中...”；
- 其他动作禁用；
- 生成成功后显示处理结果；
- 生成失败后展示错误和重试入口；
- 生成成功后尽量定位到最新结果。

### 6.2 处理结果卡片

每个处理结果应该是独立卡片：

```text
标题：润色版本 / 要点摘要 / 小红书版本
元信息：时间 / 模型 / 是否编辑过
内容：可编辑文本
操作：复制 / 编辑 / 重新生成 / 删除
```

P0 可以先做：

- 复制；
- 编辑；
- 删除。

P1 再做：

- 重新生成；
- 恢复 AI 原始版本；
- 用当前版本继续生成。

### 6.3 卡片 Tab

卡片 Tab 应更像笔记列表，而不是消息流。

列表项：

```text
标题
摘要 2-3 行
创建时间
处理状态
更多操作：重命名 / 删除 / 复制原文
```

详情空间：

```text
标题区：标题 / 时间 / 卡片操作
原文区：原始转写，可复制，可编辑标题
版本区：后处理版本列表
底部：处理操作栏
```

### 6.4 设置页

设置页暂时保持现状，但要注意：

- 连接测试结果需要更容易复制；
- API Key 不应出现在日志；
- 后处理 Base URL 的中转站兼容逻辑需要继续保留。

## 7. Implementation Roadmap

### Phase 1：交互闭环

目标：减少操作混乱，让用户能顺畅完成“记录后加工”。

任务：

1. 更多操作改为 Bottom Sheet；
2. 生成结果卡片增加局部操作；
3. 生成成功后定位最新结果；
4. 后处理失败提供局部重试；
5. 卡片详情中复用同一套底部处理栏。

### Phase 2：可编辑草稿

目标：让 AI 输出成为可修改的创作草稿。

任务：

1. 处理结果支持编辑；
2. 编辑后保存 dirty 状态；
3. 复制编辑后的内容；
4. 支持删除单个处理版本；
5. 原始转写可复制，暂不直接编辑。

### Phase 3：本地持久化

目标：让产品可日用，不因重启或更新丢内容。

任务：

1. 引入 Room；
2. 持久化 IdeaCard；
3. 持久化 ProcessingResult；
4. App 启动时恢复历史；
5. 支持删除卡片和处理版本。

### Phase 4：笔记化卡片

目标：让卡片 Tab 从消息流变成灵感笔记库。

任务：

1. 列表和详情视觉分离；
2. 卡片重命名；
3. 收藏/置顶；
4. 搜索；
5. 标签。

## 8. Open Questions

1. 原始转写是否也允许编辑？
   - 倾向：P0 不允许，避免破坏“原始记录”。
   - 可提供“创建编辑副本”。

2. 本地存储先 JSON 还是 Room？
   - 倾向：Room，因为后续会有搜索、标签、多版本。

3. 更多操作是否需要自定义？
   - 倾向：P1 做。P0 先根据使用频率固定主动作。

4. 卡片详情是否要独立页面？
   - 倾向：从交互上独立，技术上可以先保持单 Activity + Compose 状态。

5. 后处理版本是否允许多次同类型结果？
   - 倾向：允许。例如多次润色可以生成多个版本。

## 9. Next Best Step

建议下一步进入 Phase 2 的第一小步：

> 让处理结果卡片可编辑，并支持复制、删除。

原因：

- 它直接解决用户最强反馈之一；
- 改动范围可控；
- 不必先完成完整本地持久化；
- 后续持久化时只需要保存编辑后的 content。

如果要先做存储，也可以把 Phase 3 提前。但从交互体验看，“可编辑草稿”更能让用户感受到产品从工具雏形进入创作空间。
